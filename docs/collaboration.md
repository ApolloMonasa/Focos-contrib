# 一项任务怎样从认领走到合入

我们只有三个人，每人每周约 10–14 小时。一次只推进一个实现任务，另外留出时间审阅队友的 PR。大模块分成几次小交付，不要求第一次就全部完成。

## 1. 在 Issue 认领

先看 [任务入口](backlog.md)。在 Issue 里说清楚这次先做什么、预计花多久、需要谁配合；确认后把自己设为 Assignee。Assignee 就是这个模块的负责人（owner），负责推进和验收，不代表所有代码都由他写。

同时约一名备份 reviewer。成员账号与模块分工未确认前，不能代填 owner 或 CODEOWNERS。Issue 是任务状态的唯一来源，文档只放导航。

每个 Issue 保留这些信息即可：负责人、reviewer、当前下一步、依赖、spec/PR 链接、预估工时与里程碑、验收命令与结果。受阻时补上卡在哪里、需要什么帮助、最近更新时间。优先级和赛段使用标签或里程碑表达。

用「待讨论 → 写 spec → 可实现 → 实现中 → 待审阅 → 已合入 → 已验收」描述进展；阻塞单独标明。合入不等于板上已经验收。每周一起核对一次；卡住超过一天就找队友结对，两天没有进展要重新拆小任务。

## 2. 先讲清行为，再写代码

spec 是一份短说明：调用者怎么用、正常时得到什么、出错时怎么办、怎么证明做对了。放在 `specs/`，PR 链接到准确版本。新接口先让使用它的队友审阅；小修复可以在同一 PR 里改 spec 和测试。

按模块补充必要细节：内存所有权、unsafe 前提、锁顺序、是否阻塞、错误码、资源释放、写入何时持久化，以及明确不做什么。不要求每个小任务都写无关章节。

测试先失败，再实现到通过，最后重构并回归。保存能解释失败原因的记录；缺陷修复先加复现测试。失败应该来自缺失的行为，不能故意破坏编译，也不能降低断言迁就代码。失败中的开发放在个人分支，main 始终保持绿色。

## 3. 从个人 fork 提交 PR

从最新 `upstream/main` 建短分支：`spec/编号-主题`、`feat/编号-主题` 或 `fix/编号-主题`。提交方法见 [上手指南](getting-started.md)。

PR 说明让 reviewer 能回答四件事：为什么改、对应哪份 spec、实际怎么测、还有什么没验证。附关联 Issue、来源和 AI 使用记录。普通代码尽量控制在约 300 行可人工审阅的改动内；超过时说明审阅顺序，不要为了行数拆坏一个完整行为。

普通 PR 需要一名非作者批准。HAL、ABI、内存安全、持久化语义变更需要另外两人 review；接口生产者和使用者一起确认。reviewer 要检查失败路径，不能只看成功截图。用 squash 合入，发布用 tag 和完整 SHA；main 回归时优先恢复构建，再修复原因。

## 4. 按改动选择测试

| 改动 | 要交的证据 |
| --- | --- |
| 可独立运行的算法、FAT 解析、缓存、路径处理 | host 测试：在开发机上用内存盘检查正常输入、边界和失败 |
| 启动、异常、调度、用户程序、系统调用 | QEMU 集成测试：跑真实内核并检查输出、退出状态和超时 |
| arch/HAL、设备驱动、内存/DMA、写回 | 对应提交的板上冒烟日志；其余改动每周集成上板，发布候选必测 |

当前 CI 已有格式、clippy、构建和 BOOT-001。host 纯逻辑测试、双架构构建、FS/VFS 隔离和官方测例门禁随对应模块接入；不能把计划写成已通过。必过集合的调整单独提 PR，失败项目不能静默移出分母。

## 5. GitHub 已替我们强制什么？

main 的 `bootstrap` 检查必须由 GitHub Actions 提供且成功，分支须跟上 main；至少一名有写权限的非作者批准，新提交后重新审阅，最后一次推送也需要另一人批准。讨论必须解决，禁止强推/删除 main，管理员同样受限。只允许 squash 合并，适用的上游分支合并后自动清理。

上游 PR 直接跑只读令牌的 CI，main push 再复验。首次贡献者的运行可能需要维护者批准。板卡 runner 只运行维护者确认的提交，并给设备加独占锁。

两人审阅的特殊要求靠团队执行，不能误认为统一的一人门禁已经覆盖。自动代码审阅由仓库负责人手动配置；它提供建议，不能替代人工批准。具体保护配置见 [.github/main-protection.json](../.github/main-protection.json)，该文件本身不会自动改服务器设置。

## 6. 每周留下什么？

用 30 分钟一起演示本周能运行的东西。owner 更新 Issue 的进展、阻塞和证据；新成员也要轮换实现与 review，不把某个人固定成材料整理员。

性能改动同时记录 base/head SHA、设备与镜像、配置、负载、原始数据、复现命令、差异和复测结论。先在固定板上做至少 7 轮配对测试；吞吐下降超过 5% 或 p95 延迟上升超过 10%，且超出基线噪声时复测并登记 Issue。这只是初始预警线，不是已经验证的硬件阈值。功能、泄漏或持久化错误直接阻断合入。

共享 CI 的计时只做烟测。小结果与绘图脚本进 Git，大日志放可公开的 CI artifact，非公开资料存团队私有空间；候选版本另行归档，避免 artifact 过期。报名资料和凭据不进仓库。来源、AI 使用和人工核验见 [记录要求](ai-usage.md)。
