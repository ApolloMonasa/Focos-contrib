# FocOS 团队协作要求

这些是执行规则与信息要求，不是待填写的 issue、spec 或 PR 模板。成员账号确定后，将角色和目录匹配到真实 owner，再启用对应的 CODEOWNERS 规则。

## 认领和职责

每个模块有一个 owner 和一个备份 reviewer。owner 负责边界、验收和集成，不独占全部实现。首次认领先评估是否读懂相关 spec、能否运行测试；不熟悉模块的成员从内存盘、错误用例、串口解析等 3–6 小时的小任务开始，由 owner 结对 review，然后逐步认领功能。

用 upstream issues 作为任务唯一来源，模块认领表是这些 issue 的看板视图。不要同时维护一份独立、经常过期的表格。模块大任务下面分解可验收的小任务，每人同时最多一个实现任务、一个 review 任务。依赖未满足的任务不得假装进入实现阶段。

认领信息必须包含：任务 ID、模块、功能目标、区域/全国赛阶段、优先级、owner、备份 reviewer、spec 路径及版本、前置 issue、预估工时、目标里程碑、状态、分支/PR、验收命令、证据链接、阻塞原因和最近更新时间。初始任务没有认领人时明确保持未分配。

状态按「待澄清→规格审阅→可认领→已认领→实现/测试→待 review→已合入→验收完成」流转；受阻时记录依赖和下一步。合并 PR 不自动证明板上验收完成。owner 每次推进更新 issue，每周集成会上核对看板；两天无进展或阻塞超过一天就请求结对处理。无人响应的认领由团队讨论后转交，保留上下文。

## 分支和 PR

- upstream 为组织的私有 `Focos`；成员在组织允许的私有 fork 网络中开发，`origin` 指向个人 fork、`upstream` 指向组织仓库。
- 分支建议 `spec/<issue>-<topic>`、`feat/<issue>-<topic>`、`fix/<issue>-<topic>`；从最新 upstream main 分出，一次解决一个可解释的问题。
- 初始仓库必须先有一个本地通过检查的可构建基线。该初始化之后，一切功能变更走 PR；禁止向 main 直接推送、强推或将长期集成留到赛前。
- PR 关联认领 issue 与准确 spec 版本，说明可观察行为、测试结果、来源/AI 使用和剩余限制。新语义先审 spec，再实现；小修复可以在同一 PR 中明确 spec 修订及其测试。
- 普通 PR 至少一名非作者 review；HAL、ABI、内存安全、持久化语义变更由另外两名成员 review。作者不能批准自己的 PR；reviewer 必须验证关键失败路径而非只看运行截图。
- 尽量让人工审阅代码控制在约 300 行以内；生成文件、测例外部代码不计入，超出时解释如何拆分审阅。不要为满足行数拆坏一个行为的完整性。
- 接口变更需要生产者与消费者同意并同步更新；中间 PR 用兼容层或默认关闭的特性保持 main 绿色。不能合入编译失败或影响已验收能力的 PR。
- 合并采用 squash 保持问题边界，PR 历史保存 TDD 与 review 证据；发布用 tag 和完整 SHA。出现 main 回归，先恢复可构建状态，再以新 PR 修复。

## spec 与测试绑定

spec 应覆盖：目标/非目标、公开接口、输入与错误语义、资源所有权、锁顺序、可阻塞位置、unsafe 前提、持久化承诺、兼容性、验收案例和性能预算。测试名或元数据引用 spec 条目，PR 引用 spec；设计文档中的重要承诺都能追到测试或明确的未验证项。

TDD 记录以「预期行为的测试先失败→最小实现通过→重构回归」为原则。失败应来自功能缺失或错误行为，不能故意制造编译噪声充当证据。模块开发期间失败测试留在分支，main 不保留红灯。修复缺陷先补复现用例；修改断言需要解释语义依据，不能降低断言去迁就实现。

## 三层测试及 CI

| 层次 | 内容 | 触发与合入要求 |
| --- | --- | --- |
| host 单元/属性测试 | 分配器、FAT 解析/簇链/目录、缓存淘汰、路径和错误处理；内存盘、坏扇区、短 I/O、写失败注入 | 每个相关 PR 必须通过；第一批可测试纯逻辑模块合入时建立，当前启动起点尚无此类模块 |
| QEMU 集成 | 启动、异常、任务、用户 ELF、syscall、真实磁盘镜像路径、冻结的历史测例 | 每个 PR；当前已实现 BOOT-001，其余门禁随里程碑增加；失败/超时不能记为通过 |
| 板上冒烟 | 真 UART/中断/块设备、文件同步后重启校验、关键程序 | 触及 arch/HAL/驱动/内存/DMA/写回的 PR 合入前提供对应 SHA 板上日志；其余变更每周集成验证；发布候选必测 |

初始 CI 执行格式检查、裸机 clippy、构建与 QEMU 冒烟，保存环境版本和串口日志。后续门禁逐步增加 host 测试、两架构构建、FS/VFS 架构隔离检查、选定基础测例和 spec/issue 关联检查。选定的必过集合只能通过独立的范围变更 PR 修改；新发现的失败不能静默移出分母。

组织需设置 required checks、至少一名非作者 review、禁止强推、更新后重审；平台套餐或权限不支持时，明确记录缺口，由 maintainer 执行人工合入清单，不能声称已强制保护。自动 code review 是辅助反馈，不能代替非作者批准和实际测试。

2026-11-04 配置结果：组织已允许私有 fork，Focos 已启用该能力；初始 main 的 GitHub CI 已成功。分支保护 API 返回 403，提示当前套餐不支持该私有仓库功能，因此 required checks/review/禁止强推尚未由 GitHub 强制执行。当前必须由维护者人工执行上述规则；升级相应套餐后重新启用服务器门禁。不得为取得保护能力而把此仓库改为公开。

成员 fork CI 的审批按组织策略配置。无凭证的 host/QEMU 检查优先放普通 CI；连接真实板卡的 runner 只执行维护者确认的提交，使用独占锁避免争抢设备。不要用携带 upstream 凭证的工作流执行未经审阅的 fork 代码。

## 性能回归与证据维护

普通共享 CI 只做功能与性能烟测，不把抖动大的耗时变成硬门槛。稳定板上环境维护固定基线，至少 7 轮配对运行，先学习噪声：吞吐下降超过 5% 或 p95 延迟上升超过 10%，且超出基线噪声区间时触发复测与性能 issue。这些是初始预警阈值，不是已验证的设备阈值。确认的退化必须修复或在 PR 中有明确的权衡批准。

每条回归记录包含 base/head SHA、spec/PR、设备与镜像、配置、工作负载、每轮原始数据、噪声范围、图表生成命令、变化幅度、复测结论和处理结果。功能断言、资源泄漏与持久化错误立即阻断，不受性能容忍阈值影响。

版本化小型 JSON/CSV 结果与绘图脚本，大日志/镜像放私有 CI artifact 或团队存储，记录校验和与保留期限。比赛候选版本应额外归档，避免 CI artifact 到期导致证据丢失。个人报名材料始终留在工作区 `enroll_info/`，不进入代码库、日志或公开材料。

按 2026 区域赛章程记录 AI 工具、使用场景、受影响文件、人工复核与验证结果；借鉴代码记录来源版本、许可证与本队增量。开发历史是过程性资料的一部分，不能赛前补造。
