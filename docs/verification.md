# 怎样证明基本功能做对了

**当前状态：历史官方测试尚未在 FocOS 上运行。** 已验证的只有启动用例 BOOT-001。不要把下面的测试计划当成通过成绩。

## 我们先用哪套测试？

区域赛先用 `pre-2024`：它使用 FAT32，适合当前实现方向。已核对源码和配套 judge，共 32 个测试程序；首批 P0 候选 16 个。P0 表示优先完成，P1 表示后续扩展。

- [测试清单](../tests/catalog.json)：要运行什么、依赖什么，目前结果都是 NOT_RUN。
- [版本锁定](../tests/sources.lock.json)：引用哪个仓库、分支和完整提交 SHA。
- [接入任务 #8](https://github.com/MindScrath/Focos/issues/8)：从这里认领。

## 接入人员先做这四步

1. 按锁定版本取得源码，先单独构建一个简单程序，如 `write`；确认 ELF 架构、ABI 和辅助文件。
2. 在参考 Linux/QEMU 环境跑同一产物，核对 judge 如何判成功和失败，记录完整命令。当前仓库还没有可直接运行全部官方测例的命令，需要在 #8 中交付。
3. 用户态和 syscall 可用后，再接入 FocOS。逐项保存输出、退出状态和超时；注入失败输出，确认解析器不会误判为成功。
4. 更新结果，附内核、测试、judge 的 SHA，镜像哈希、环境、命令和原始日志。写入测试还要检查实际文件内容。

## 提前避开三个坑

旧 runner 只有 31 个入口，漏了 `sleep`，还引用不存在的 `yield.sh`。补运行入口时保留独立适配记录，不修改被测程序的语义。`exit.c` 内部依赖 fork/wait，所以它不是最早能跑的简单退出测试。`mount` 需要真实可挂载设备和目录，不能只让系统调用返回成功。

## 结果怎么展示

每项标为 PASS、FAIL、TIMEOUT、NOT_RUN 或 BLOCKED_BY_DEPENDENCY，并写明原因。展示“通过 X / 冻结总数 Y”，失败和未运行项都保留。启动标记、部分断言成功和整个测试通过是三回事。

对外写清是“历史官方测试原环境”还是“FAT32 打包/运行适配”。团队自测和当届正式得分另列。官方测试覆盖不到的坏指针、OOM、簇链环、跨簇写、同步重启、异常隔离等，需要自己补测。

## 以后扩到哪些分支？

FAT32 基础功能稳定后，从 `final-2023` 选能运行的文件负载；全国赛再研究 `pre-2025` 双架构原环境、`final-2025` 存储专项和当届正式规则。Ext4 镜像不能直接交给 FAT32 读取。

全部 19 个分支的比较、测试到功能的映射及结果包要求，见 [详细审计记录](reference/test-audit.md)。做具体接入时再读对应部分。
